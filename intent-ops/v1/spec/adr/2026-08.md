## 2026-08-27: ADR-0001 — intent-ops package architecture

> **Status**: Accepted
> **Date**: 2026-08-27
> **Owner**: package maintainer

### Context

The `intent-ops` package merges two systems — the AI-oriented kanban (delivery flow) and the spec-first docs system (canonical knowledge) — into one copyable package. Without a defined architecture, lane READMEs pointed at an origin project's `docs/` paths, breaking the copy promise.

### Decision

The package is self-contained: `instructions.md` is the navigator; `v1/flow/` is the kanban (lanes + templates); `v1/spec/` is the spec-first docs system; `v1/cli/init.md` is the genesis rollout plan. Every internal reference resolves inside the package; no runtime dependency on origin folders.

### Consequences

- ✅ Copyable into any project; navigation starts at `instructions.md`.
- ✅ Link integrity and version scope are enforceable by scan gates.
- ⚠️ The package must be kept free of origin business content to remain reusable.

## 2026-08-27: ADR-0002 — Versioned layout: v1 current, v2 by file copy

> **Status**: Accepted
> **Date**: 2026-08-27
> **Owner**: package maintainer

### Context

The package is expected to evolve. A naive version model (branch-per-version, partial references) makes upgrades error-prone.

### Decision

`v1/` is the complete current version. The next version (`v2/`) is created by copying all files under `v1/` to `v2/` and applying changes. No cross-version links and no partial-version references. `v1/README.md` documents the migration checklist.

### Consequences

- ✅ Migration is a plain file copy; each version is a whole-folder snapshot.
- ⚠️ Version-scope discipline must be maintained by scan gates or migration breaks silently.

## 2026-08-27: ADR-0003 — Promotion path: `v1/spec/` ↔ `<project>/docs/`

> **Status**: Accepted
> **Date**: 2026-08-27
> **Owner**: package maintainer

### Context

A target project may want its canonical docs at a conventional `<project>/docs/` location instead of `intent-ops/v1/spec/`.

### Decision

Both are valid: keep `v1/spec/` as-is, or promote it by renaming the folder to `<project>/docs/`. All internal links are relative and survive the rename as long as the folder structure is preserved. The choice is recorded here.

### Consequences

- ✅ Zero-structural-change promotion; the flow templates reference `v1/spec/...` in prose and relative `../../spec/...` links, both portable.
- ⚠️ If a project renames the folder, prose mentions of `v1/spec/` become descriptive, not literal paths.

## 2026-08-27: ADR-0004 — Recursive self-generation: `v1/cli/init.md` is a genesis rollout plan

> **Status**: Accepted
> **Date**: 2026-08-27
> **Owner**: package maintainer

### Context

The spec-first scaffold under `v1/spec/` must be initialized consistently in every target project. An instruction sheet would be non-gated and non-verifiable.

### Decision

`v1/cli/init.md` is itself a rollout plan (per `v1/flow/templates/rollout-plan-template.md`): Summary, Docs Impact with decision evidence, phased execution with verification gates, mandatory closing phases. Executing it generates all folders and files inside `v1/spec/`. The package bootstraps its own spec system through its own methodology.

### Consequences

- ✅ Deterministic, gated, re-executable initialization in any project.
- ✅ The recursion is provable: executing the genesis plan regenerates the scaffold.
- ⚠️ The genesis plan's file inventory must stay aligned with the actual `v1/spec/` tree, enforced by verification gates.

## 2026-08-27: ADR-0005 — Skills folder: package-root registry, linked/navigated, integrated on init

> **Status**: Accepted
> **Date**: 2026-08-27
> **Owner**: package maintainer

### Context

Community-downloaded AI-coding instructions (skills) need a home in the package. Without a defined folder, registry, and init integration, skills would land ad-hoc and never be discovered or wired into the workflow.

### Decision

`skills/` is a package-root folder for community skills, with `skills/README.md` as its registry/index. Skills are **linked** from the package entry points (`instructions.md`, `README.md`), **navigated** via the registry + assistant context index, and **integrated** when users init their workflow: the genesis plan (`v1/cli/init.md`) gains a Skills-integration phase that refreshes the registry, registers skills for retrieval, and validates links. `skills/` is package-root user content, not versioned under `v1/`; references from `v1/`-rooted docs to the registry are a documented package-root external (whitelisted in the version-scope scan).

### Consequences

- ✅ Skills are discoverable (navigator → registry → context index) and integrated on init.
- ✅ The v1 → v2 migration is unaffected: `skills/` is copied with the package folder, not under `v1/`.
- ⚠️ Skills must still obey the business-free rule and the docs-first governance (no skipping `Docs Needed` / decision evidence).

## 2026-08-27: ADR-0006 — Relocation: `intent-ops` extracted to its own standalone repo

> **Status**: Accepted
> **Date**: 2026-08-27
> **Owner**: package maintainer

### Context

The package must be copyable into any project independently. Living inside the origin project couples it to project-local folders (`ai_oriented_kanban/`, `docs/`) and mixes it with project delivery records, which makes versioning, discovery, and community reuse awkward. User-confirmed 2026-08-27: `intent-ops` relocates to its own standalone repo; the origin folders are used only by the current project and are not reusable for new projects — no backport flow needed.

### Decision

`intent-ops` is extracted to its own standalone repo. The relocated package contains only the **reusable surface**: navigator (`instructions.md`), package README, `skills/` registry, and `v1/` (`flow/` lane READMEs + templates, `spec/` scaffold incl. ADR history, `cli/init.md` genesis plan). Project-specific flow-lane working docs (plan records, archives, reports) stay in the origin project's copy — flow lanes are blank in fresh copies per ADR-0004. The relocation decision itself is recorded here per the Follow-Up Phase 3 verification gate.

### Consequences

- ✅ Package is versionable and copyable independently of any origin project; origin project keeps its usage copy and delivery history.
- ✅ Version model (v1 → v2 by file copy, ADR-0002) and genesis recursion (ADR-0004) are unaffected by relocation.
- ⚠️ Improvements must be authored in the standalone repo and synced back to usage copies deliberately (one-way extraction, reverse flow manual).
